# CodeInsight：基于 LangChain 的智能代码解释与审查系统

## 1. 项目概述

### 1.1 项目名称

**CodeInsight：基于 LangChain 的智能代码解释与审查系统**

### 1.2 项目背景

初学编程的学生和初级开发者在阅读代码、排查错误、分析算法复杂度和编写测试用例时，往往需要花费较多时间。传统的静态检查工具能够发现部分语法和规则问题，但通常不能直接提供易于理解的自然语言解释。

本项目计划开发一款基于 LangChain 和大语言模型的轻量级编程辅助应用。用户提交代码并选择分析模式后，系统调用大语言模型生成代码解释、潜在问题审查、复杂度分析和测试用例，并以结构化报告的形式展示结果。

### 1.3 项目目标

1. 帮助用户快速理解陌生代码的功能、执行流程和关键算法。
2. 识别代码中可能存在的语法、逻辑、边界条件及性能问题。
3. 分析算法的时间复杂度和空间复杂度，并说明推导依据。
4. 根据代码生成具有代表性的测试用例及预期结果。
5. 将分析结果整理为结构化、易阅读、便于复制和导出的报告。
6. 通过 LangChain 将提示词、模型调用和结果解析组织为清晰的应用流程。

### 1.4 目标用户

- 计算机相关专业学生；
- 编程初学者；
- 需要快速理解或初步审查代码的初级开发者。

### 1.5 项目范围

| 项目内容 | 第一版要求 |
|---|---|
| 支持语言 | C++、Java、Python |
| 代码输入 | 粘贴代码、选择编程语言 |
| 代码解释 | 必须实现 |
| 代码审查 | 必须实现 |
| 复杂度分析 | 必须实现 |
| 测试用例生成 | 必须实现 |
| 在线大模型接入 | 必须实现 |
| 本地模型切换 | 可选扩展 |
| 用户登录与权限管理 | 暂不实现 |
| 多智能体协作 | 暂不实现 |
| 自动修改并执行任意代码 | 暂不实现 |

> 说明：大模型对语法错误的判断不能完全替代编译器或解释器。若要确认代码能否编译运行，应调用相应语言工具链进行验证；第一版可以先由模型解释潜在语法问题。

## 2. 功能模块结构

系统分为四层：

1. **用户交互层**：负责代码输入、分析模式选择、参数设置和报告展示。
2. **业务处理层**：接收用户请求，执行输入校验，并调用对应分析模块。
3. **LangChain 编排层**：负责提示词模板、模型调用、结构化输出和异常处理。
4. **模型服务层**：连接在线大模型 API；可选连接本地部署模型。

核心业务模块包括：

- 代码解释；
- 代码审查；
- 算法复杂度分析；
- 测试用例生成；
- 分析报告展示与导出。

## 3. 详细功能需求

优先级定义：

- **P0：必须实现**，构成课程作业的核心版本。
- **P1：建议实现**，能够提升完整性和演示效果。
- **P2：可选扩展**，时间充足时再开发。

### 3.1 代码输入与管理模块

| 编号 | 功能名称 | 优先级 | 具体需求 | 验收标准 |
|---|---|---|---|---|
| F-01 | 代码输入 | P0 | 提供多行代码编辑区域 | 能粘贴并完整显示多行代码 |
| F-02 | 语言选择 | P0 | 支持 C++、Java、Python | 选择的语言会传入分析模块 |
| F-03 | 输入校验 | P0 | 检查空代码及超长输入 | 空代码不能提交；超长输入有明确提示 |
| F-04 | 示例代码 | P1 | 提供可加载的示例代码 | 点击示例后可直接进行分析 |
| F-05 | 清空代码 | P1 | 清除编辑区域内容 | 输入区域恢复初始状态 |
| F-06 | 分析模式选择 | P0 | 可选择解释、审查、复杂度分析或测试生成 | 系统执行对应分析流程 |

第一版建议使用普通多行文本框；若开发时间充足，可使用 Monaco Editor 增加语法高亮。无需一开始就实现完整 IDE。

### 3.2 代码解释模块

**优先级：P0**

| 编号 | 功能名称 | 具体需求 |
|---|---|---|
| F-07 | 整体功能解释 | 用自然语言说明代码的主要用途 |
| F-08 | 执行流程分析 | 按程序执行顺序解释主要步骤 |
| F-09 | 关键语句解释 | 解释重要变量、函数、循环和条件分支 |
| F-10 | 算法思路说明 | 对算法代码说明核心思路 |
| F-11 | 输入输出分析 | 根据代码识别预期输入、输出及其格式 |
| F-12 | 重点代码定位 | 尽可能标明相关函数名、行号或代码片段 |

建议报告包含以下部分：

1. **整体功能**：程序的用途及主要结果。
2. **执行流程**：程序执行的关键步骤。
3. **关键语句**：重要变量、函数和控制结构的作用。
4. **输入与输出**：输入格式、输出内容及必要的假设。
5. **算法思路**：程序采用的主要算法或处理方法。

#### 示例输出

假设代码用于计算整数数组元素之和：

- **整体功能**：遍历数组并累加所有元素，最后返回总和。
- **执行流程**：初始化累加变量；依次访问数组元素；将元素加入累加变量；返回结果。
- **关键语句**：`sum += arr[i]` 将当前元素累加到结果中。
- **时间复杂度**：`O(n)`，其中 `n` 是数组长度。
- **额外空间复杂度**：在不计输入数组的前提下为 `O(1)`。

### 3.3 代码审查模块

**优先级：P0**

| 编号 | 功能名称 | 具体需求 |
|---|---|---|
| F-13 | 逻辑问题检查 | 识别条件判断、循环边界、返回值等潜在错误 |
| F-14 | 边界条件检查 | 检查空输入、极值、数组越界、空指针等风险 |
| F-15 | 异常处理检查 | 识别可能导致程序异常退出的情况 |
| F-16 | 代码质量检查 | 识别重复代码、命名不清、结构过于复杂等问题 |
| F-17 | 性能问题检查 | 识别重复计算、低效算法等问题 |
| F-18 | 严重程度分类 | 将问题标记为高、中、低优先级 |
| F-19 | 问题定位 | 尽可能给出函数名、行号和相关代码片段 |
| F-20 | 修复建议 | 解释问题原因并给出建议修改方式 |

建议采用以下严重程度标准：

- **高**：可能造成明显错误结果、崩溃、越界访问或严重安全风险。
- **中**：在特定输入下可能出现错误，或存在较明显的性能问题。
- **低**：主要影响可读性、可维护性或轻微性能表现。

审查报告建议包含：

- 问题标题；
- 问题类型；
- 严重程度；
- 代码位置；
- 相关代码片段；
- 问题原因；
- 可能影响；
- 修改建议；
- 建议的验证方法。

> 大模型输出应表述为“发现的潜在问题”或“待验证问题”，不应将未经测试的判断直接认定为确定存在的 Bug。

### 3.4 算法复杂度分析模块

**优先级：P0**

| 编号 | 功能名称 | 具体需求 |
|---|---|---|
| F-21 | 时间复杂度分析 | 估算程序运行时间随输入规模变化的增长趋势 |
| F-22 | 空间复杂度分析 | 分析额外变量、递归调用和辅助数据结构的空间开销 |
| F-23 | 复杂度推导 | 解释循环嵌套、递归或主要操作的复杂度来源 |
| F-24 | 优化建议 | 提出可行的优化思路，并比较优化前后的复杂度 |

复杂度分析结果应包含：

- 时间复杂度；
- 空间复杂度；
- 关键推导过程；
- 复杂度成立的前提或假设；
- 可行的优化建议（若存在）。

对于复杂递归、动态规划或依赖特定数据结构的代码，系统应允许输出“不确定”或说明分析假设，不应强行给出缺乏依据的结论。

复杂度分析属于静态推理，不等同于实际运行性能测试。

### 3.5 测试用例生成模块

**优先级：P0**

| 编号 | 功能名称 | 具体需求 |
|---|---|---|
| F-25 | 正常用例生成 | 生成符合预期使用场景的输入 |
| F-26 | 边界用例生成 | 覆盖空输入、极值、最小规模等情况 |
| F-27 | 异常用例生成 | 在适用情况下生成非法输入或异常场景 |
| F-28 | 预期结果说明 | 给出每组测试的预期输出或行为 |
| F-29 | 用例覆盖说明 | 说明每组测试用例验证的行为 |

测试用例建议以表格展示：

| 测试类型 | 输入 | 预期结果 | 测试目的 |
|---|---|---|---|
| 普通输入 | `[1, 2, 3]` | `6` | 检查基本累加逻辑 |
| 空数组 | `[]` | `0` | 检查空输入处理 |
| 单元素 | `[5]` | `5` | 检查最小非空输入 |
| 含负数 | `[-2, 3]` | `1` | 检查负数处理 |

以上仅是假设被测函数用于计算整数数组之和时的示例。实际生成的测试用例必须与提交代码的接口、输入格式和行为约定相匹配。

### 3.6 分析报告与交互模块

**优先级：P0，报告导出为 P1**

| 编号 | 功能名称 | 优先级 | 具体需求 |
|---|---|---|---|
| F-30 | 结构化展示 | P0 | 将不同分析结果展示在独立区域 |
| F-31 | 分析状态提示 | P0 | 显示正在分析、成功、失败等状态 |
| F-32 | 错误提示 | P0 | 对 API 超时、模型调用失败、结果解析失败给出提示 |
| F-33 | 复制结果 | P1 | 支持复制分析文本或测试用例 |
| F-34 | 重新分析 | P0 | 修改代码后可再次提交 |
| F-35 | 报告导出 | P1 | 支持导出 Markdown 格式的分析报告 |

第一版不要求实现用户账户体系，也不要求永久存储所有分析记录。能够稳定完成代码输入、分析、结果展示和重新分析，即可构成完整的基本流程。

## 4. 技术架构与技术选型

### 4.1 推荐技术栈

| 技术 | 推荐方案 | 用途 |
|---|---|---|
| 开发语言 | Python | 实现后端业务逻辑 |
| 大模型编排 | LangChain | 组织提示词、模型调用和输出解析 |
| Web 界面 | Streamlit | 快速搭建交互页面 |
| 在线模型 | 对应厂商的 LangChain 集成包 | 生成解释与审查报告 |
| 本地模型（可选） | Ollama + 兼容模型 | 本地推理 |
| 语法检查（可选增强） | 编译器或解释器 | 验证语法和部分运行错误 |
| 数据存储（可选） | SQLite | 保存分析历史和用户设置 |

### 4.2 LangChain 的使用方式

建议设计四个独立分析流程，共享统一的模型配置：

1. **代码解释流程**：输入代码与语言信息，返回代码解释报告。
2. **代码审查流程**：输入代码与语言信息，返回问题列表和修复建议。
3. **复杂度分析流程**：返回时间复杂度、空间复杂度和推导过程。
4. **测试生成流程**：返回测试输入、预期输出和覆盖目的。

推荐使用的组件：

- `ChatPromptTemplate`：构造各分析模块的提示词。
- `ChatOpenAI` 或相应厂商的聊天模型集成：接入在线模型。
- `ChatOllama` 或相应的本地模型集成：接入兼容的本地模型。
- Pydantic 结构化输出：约束问题列表、复杂度结论和测试用例的数据格式。

具体模型类和结构化输出方法应以所选 LangChain 版本及模型服务的兼容情况为准。第一版可以只接入一种在线模型；如果后续需要支持本地模型，再抽象统一的模型配置接口。

### 4.3 典型数据流

1. 用户输入代码，选择编程语言和分析模式。
2. 前端检查必填项和输入长度。
3. 后端将请求交给对应分析模块。
4. LangChain 将代码、语言和分析要求填入提示词模板。
5. 模型生成分析结果。
6. 后端校验并整理返回的数据结构。
7. 前端展示报告；若调用失败，则展示错误提示并允许重试。

## 5. 非功能性需求

| 类别 | 要求 |
|---|---|
| 易用性 | 主要操作可以在单个页面完成，界面清晰 |
| 可维护性 | 输入处理、模型调用、提示词和报告展示分层实现 |
| 可靠性 | 模型异常或返回格式错误时，系统不能直接崩溃 |
| 可解释性 | 审查结论尽量包含原因和代码位置 |
| 安全性 | 不在前端暴露 API 密钥；限制输入大小 |
| 隐私性 | 提醒用户不要提交密码、密钥和其他敏感代码 |
| 性能 | 对输入长度设置上限，并提供请求超时提示 |
| 可测试性 | 准备固定代码样例和预期检查点，验证各模块输出 |

若未来增加自动运行用户代码的功能，应使用隔离环境、资源限制和执行超时。第一版建议只生成测试用例，不自动执行用户提交的代码，以降低安全风险和开发复杂度。

## 6. 开发阶段与验收计划

### 第一阶段：最小可用版本

**优先级：必须完成**

开发内容：

- 代码输入和语言选择；
- 在线模型接入；
- 代码解释；
- 代码审查；
- 基础结果展示；
- 模型调用失败时的错误提示。

验收标准：

- 能够提交示例代码并获得结构清晰的解释报告；
- 能够生成潜在问题及修复建议；
- 模型调用失败时，页面不会直接崩溃。

### 第二阶段：补齐核心分析能力

**优先级：必须完成**

开发内容：

- 算法复杂度分析；
- 测试用例生成；
- 结构化输出和格式校验；
- 复制结果；
- 固定样例测试。

验收标准：

- 四种分析模式均能独立运行；
- 报告包含约定的主要字段；
- 常见异常输入得到妥善处理。

### 第三阶段：提升演示质量

**优先级：选做**

可选开发内容：

- 编译器或解释器语法检查；
- Markdown 报告导出；
- 本地模型切换；
- 分析历史；
- 代码语法高亮。

验收标准：

- 至少完成一项扩展功能；
- 能通过演示样例说明扩展功能的实际作用。

## 7. 测试计划

建议准备固定测试集，至少覆盖以下场景：

| 测试编号 | 测试场景 | 预期检查点 |
|---|---|---|
| T-01 | 正常代码 | 能生成对应分析报告 |
| T-02 | 包含明显逻辑缺陷的代码 | 能指出潜在问题并解释原因 |
| T-03 | 包含边界条件风险的代码 | 能识别相关输入场景 |
| T-04 | 复杂度较明显的循环代码 | 能给出合理的复杂度推导 |
| T-05 | 具有明确输入输出的函数 | 能生成与函数行为相符的测试用例 |
| T-06 | 空代码 | 前端阻止提交并给出提示 |
| T-07 | 超长代码 | 提示输入长度限制 |
| T-08 | 模型服务不可用 | 显示错误信息并允许重试 |
| T-09 | 模型返回格式不符合预期 | 后端捕获解析错误，不直接崩溃 |
| T-10 | 不同编程语言的示例 | 能将语言信息正确传递给模型 |

建议另外设置 20–30 个固定问题或代码样例，记录报告完整性、问题定位质量和测试用例合理性。评估时应区分“格式完整”和“内容正确”，不能仅凭输出结构正确就认定分析准确。

可进一步对比两种方案：

- 直接使用普通提示词调用模型；
- 使用结构化提示词与输出校验调用模型。

比较两者在字段完整性、报告规范性和问题定位方面的表现。

## 8. 最终提交成果

课程作业建议提交以下内容：

1. **可运行的源代码**：包含界面、业务逻辑、模型调用和配置文件。
2. **结构化需求说明书**：使用本文的模块编号与验收标准。
3. **系统设计文档**：包括架构图、模块说明、数据流和调用流程。
4. **测试报告**：覆盖正常代码、逻辑缺陷、边界条件和模型异常场景。
5. **演示材料**：展示代码如何经过解释、审查、复杂度分析和测试用例生成，最终得到报告。

## 9. 第一版开发范围建议

为了控制课程作业的复杂度，第一版应优先完成：

- F-01 至 F-03：代码输入和校验；
- F-06 至 F-24：四类核心分析能力；
- F-25 至 F-32：测试生成、报告展示和错误处理；
- F-34：重新分析。

F-04、F-05、F-33、F-35 以及本地模型、数据库持久化和语法检查可以根据时间安排逐步补充。

**最终建议：** 第一版围绕四种核心分析能力和统一报告格式开发。将本地模型、自动执行代码、登录系统和数据库持久化作为可选扩展，既能保证项目边界明确，也能展示 LangChain 在大模型应用工程中的实际价值。
